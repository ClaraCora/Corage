# Windows 服务已运行但内核无法启动：诊断与修复说明

最后更新：2026-08-26

适用范围：Clash Verge Rev 2.5.2、2.5.4-rc.1，以及使用 `clash_verge_service` 的后续构建。

## 先纠正一个判定错误

下面的结果**不是修复完成**：

```text
sc.exe query clash_verge_service
STATE              : 4  RUNNING
```

它只表示 Windows 服务控制管理器（SCM）看到了一个正在运行的服务进程。它不能证明：

- 服务和当前应用使用同一 IPC 协议；
- 服务接受了当前 Windows 用户的身份凭据；
- 服务已成功启动 mihomo 内核；
- TUN 已由 Service 模式接管。

真正的完成条件是在**重新打开当前版本的应用后**，应用日志依次出现：

```text
Starting core in service mode
服务成功启动核心
```

且其后没有同一次启动的 Service/Core 错误。没有这两条日志时，不能把“服务 `RUNNING`”报告为已修复。

这也是此前其他机器虽然按旧说明操作、却仍不能启动内核的原因：旧说明把中间状态当成了最终结果。

## 问题分层

| 层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| `sc.exe query` 为 `RUNNING` | 服务控制进程已注册并运行 | 协议、用户凭据、内核启动 |
| 服务版本探测成功 | 当前应用可以和服务通信 | 当前配置和内核一定可启动 |
| `服务成功启动核心` | 服务已接受凭据并启动当前用户的内核 | TUN 的实际流量效果 |
| TUN 开启且能正常联网 | 整个 Service/TUN 链路可用 | 无 |

不要先删除 `.repair.lock`。它是服务安装器的互斥锁文件；看见文件存在不等于锁仍被占用。属主、token、协议和运行时资源是不同的问题，必须按日志分支处理。

## 1. 先确定真实数据目录

普通安装版的数据目录是：

```text
%APPDATA%\io.github.clash-verge-rev.clash-verge-rev
```

便携版不是这个目录。若 `clash-verge.exe` 同级存在 `.config\PORTABLE`，真实数据目录是：

```text
<clash-verge.exe 所在目录>\.config\io.github.clash-verge-rev.clash-verge-rev
```

不要对普通安装路径和便携版路径同时执行属主或 token 操作。修错目录不会修复当前运行的应用。

下面的 PowerShell 用于生成诊断快照。将 `$AppDirectory` 改为**当前要启动的** `clash-verge.exe` 所在目录；普通安装通常是 `C:\Program Files\Clash Verge`。先在普通 PowerShell 中运行即可。

```powershell
$AppId = 'io.github.clash-verge-rev.clash-verge-rev'
$AppDirectory = 'C:\Program Files\Clash Verge' # 便携版请改为实际解压目录
$PortableFlag = Join-Path $AppDirectory '.config\PORTABLE'
$IsPortable = Test-Path -LiteralPath $PortableFlag

if ($IsPortable) {
    $AppDataRoot = Join-Path $AppDirectory ".config\$AppId"
} else {
    $AppDataRoot = Join-Path $env:APPDATA $AppId
}

$TokenPath = Join-Path $AppDataRoot '.clash-verge-service-owner-token'
$AppExe = Join-Path $AppDirectory 'clash-verge.exe'
$Service = Get-CimInstance Win32_Service -Filter "Name='clash_verge_service'" -ErrorAction SilentlyContinue
$LogFiles = @(Get-ChildItem -LiteralPath (Join-Path $AppDataRoot 'logs') -Recurse -File -Filter '*.log' -ErrorAction SilentlyContinue |
    Sort-Object LastWriteTime)

function Show-EntryAcl([string]$Path) {
    if (Test-Path -LiteralPath $Path) {
        Write-Output "=== ACL: $Path ==="
        Get-Item -LiteralPath $Path -Force | Format-List FullName,Length,Mode,Attributes
        Get-Acl -LiteralPath $Path | Format-List Owner,AccessToString
    } else {
        Write-Output "=== Missing: $Path ==="
    }
}

[ordered]@{
    User = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
    Sid = [System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value
    AppDirectory = $AppDirectory
    AppExeExists = Test-Path -LiteralPath $AppExe
    Portable = $IsPortable
    AppDataRoot = $AppDataRoot
    ServiceState = $Service.State
    ServiceStartName = $Service.StartName
    ServicePath = $Service.PathName
} | Format-List

Show-EntryAcl $AppDataRoot
Show-EntryAcl $TokenPath

Write-Output '=== SCM service query ==='
sc.exe query clash_verge_service

Write-Output '=== Recent Service/Core diagnostics ==='
if ($LogFiles.Count -eq 0) {
    Write-Output 'No application log files found.'
} else {
    $Pattern = 'Starting core in service mode|服务成功启动核心|启动核心失败|owner credential|owner token|protocol version|named pipe|InvalidRuntimeAsset|service unavailable|服务.*失败'
    Select-String -Path $LogFiles.FullName -Pattern $Pattern -CaseSensitive:$false |
        Select-Object -Last 80 | Format-Table -AutoSize
}
```

将这段输出连同最近 100 到 200 行应用日志保留。交给其他 AI 或人工排查时，必须要求其给出：真实数据目录、当前应用目录、服务路径、匹配到的最后一个错误，以及最终两条成功日志。只报告 `RUNNING` 的结论视为未完成。

## 2. 按错误修复

### 2.1 `owner credential path has an unexpected owner`

该错误表示服务拒绝了应用数据**根目录**的属主，而不只是 token 文件。典型情况是目录属主为 `BUILTIN\Administrators`，当前登录用户却是普通用户 SID。

先完全退出 Clash Verge。在受影响用户自己的会话中，以管理员方式打开 PowerShell。不要用另一个管理员账户运行，否则 `whoami` 可能不是实际使用 Clash Verge 的用户。

```powershell
# 使用第 1 节已经确认的真实 $AppDataRoot；这里以普通安装版为例。
$AppDataRoot = Join-Path $env:APPDATA 'io.github.clash-verge-rev.clash-verge-rev'
$Owner = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name

& icacls.exe $AppDataRoot /setowner $Owner
if ($LASTEXITCODE -ne 0) { throw 'Failed to set the application data directory owner.' }
Get-Acl -LiteralPath $AppDataRoot | Select-Object Owner
```

如果 `icacls` 明确提示拒绝访问，仍在同一受影响用户的管理员 PowerShell 中只取得该根目录的属主，然后重新执行上一段：

```powershell
& takeown.exe /F $AppDataRoot /D Y
if ($LASTEXITCODE -ne 0) { throw 'Failed to take ownership of the application data directory.' }
& icacls.exe $AppDataRoot /setowner $Owner
if ($LASTEXITCODE -ne 0) { throw 'Failed to set the application data directory owner.' }
```

不要添加 `/R` 或 `/T`。这里故意只修改根目录的属主，不递归改配置、订阅、节点或其他文件 ACL。

本仓库本次修复后的新构建会在生成服务凭据前自动执行同样的安全预检：只接受普通目录，不跟随重解析点，不递归修改内容；属主不匹配时尝试改回当前用户并再次验证。旧构建仍需要按本节手动修复。

### 2.2 `owner token file has an unexpected owner` 或 token DACL 错误

先完成 2.1。若根目录属主正确后仍然是 token 错误，先检查 token 必须是 32 字节的普通文件。应用关闭后，优先备份并移动单个 token，让应用重新创建受保护的凭据：

```powershell
$AppDataRoot = Join-Path $env:APPDATA 'io.github.clash-verge-rev.clash-verge-rev'
$TokenPath = Join-Path $AppDataRoot '.clash-verge-service-owner-token'
$BackupPath = "$TokenPath.invalid-$(Get-Date -Format 'yyyyMMdd-HHmmss')"

Get-Item -LiteralPath $TokenPath -Force | Format-List FullName,Length,Mode,Attributes
Move-Item -LiteralPath $TokenPath -Destination $BackupPath -ErrorAction Stop
```

重新打开应用后，它会生成新的 32 字节 token 和受保护的 DACL。不要删除整个应用数据目录。

### 2.3 `service protocol version does not match`

这表示应用与已安装 Service helper 来自不同版本。最常见错误是先用 `2.5.2` 的安装器安装服务、再直接升级应用到 `2.5.4`。

服务安装器必须来自**当前要启动的应用目录**，不能从旧安装目录、下载目录或另一台机器复制。以下命令中的 `$AppDirectory` 必须和第 1 节一致：

```powershell
$AppDirectory = 'C:\Program Files\Clash Verge' # 或当前便携版目录
$ResourceDirectory = Join-Path $AppDirectory 'resources'
$Installer = Join-Path $ResourceDirectory 'clash-verge-service-install.exe'
$Uninstaller = Join-Path $ResourceDirectory 'clash-verge-service-uninstall.exe'

if (-not (Test-Path -LiteralPath $Installer)) { throw "Current-version installer not found: $Installer" }

# 当前安装器会停止旧服务、替换 helper、重新启动并做协议就绪探测。
$Result = Start-Process -FilePath $Installer -Verb RunAs -Wait -PassThru
if ($Result.ExitCode -ne 0) { throw "Service installer failed with exit code $($Result.ExitCode)" }
sc.exe query clash_verge_service
```

如果同一版本安装器退出成功后，应用仍然报告协议不匹配，再执行一次完全重装：

```powershell
if (-not (Test-Path -LiteralPath $Uninstaller)) { throw "Current-version uninstaller not found: $Uninstaller" }
$Result = Start-Process -FilePath $Uninstaller -Verb RunAs -Wait -PassThru
if ($Result.ExitCode -ne 0) { throw "Service uninstaller failed with exit code $($Result.ExitCode)" }

$Result = Start-Process -FilePath $Installer -Verb RunAs -Wait -PassThru
if ($Result.ExitCode -ne 0) { throw "Service installer failed with exit code $($Result.ExitCode)" }
sc.exe query clash_verge_service
```

不要先使用 `sc.exe delete`。当前版本卸载器会等待服务停止并从 SCM 注销；直接删除注册项会跳过它的清理和诊断。

### 2.4 `failed to connect to named pipe ... (os error 2)`

如果该错误只出现一次，随后出现 `服务成功启动核心`，它是服务接管时的短暂重试，不需要处理。

如果该错误持续出现且没有成功启动日志，收集第 1 节的日志。此时可能是服务未就绪、协议不匹配、凭据被拒绝，或运行时资产被拒绝；不能仅凭 `sc.exe query` 判断原因。

### 2.5 `InvalidRuntimeAsset`、配置验证失败或内核自身错误

这类错误意味着 Service 已经过了注册和凭据阶段，但无法使用当前的内核文件、运行时配置或资源启动。它不是目录属主问题，也不应删除锁文件。保留应用日志与 `logs\service` 下的 core 日志，按具体错误修复内核路径、配置或资源文件。

## 3. 重启后的严格验收

1. 完成对应修复后，以普通用户身份重新启动当前版本的 Clash Verge。
2. 不要把 `clash-verge.exe` 设置成“始终以管理员身份运行”。服务负责特权；主应用长期 elevated 时，TUN 服务不可用的分支会回退到 Sidecar，掩盖真正的服务故障。
3. 启用 Service 模式与 TUN。
4. 在同一次应用启动日志中确认：

```text
Starting core in service mode
服务成功启动核心
```

5. 再确认 `clash_verge_service` 仍为 `RUNNING`，并进行实际联网测试。

只有五项都成立，才可记录为“已修复”。

## 4. 旧锁的极窄处理条件

`.repair.lock` 只在以下条件全部满足时才是候选原因：

1. 当前版本安装器持续报告 `Service repair is already in progress`；
2. Clash Verge、`clash-verge-service.exe` 和安装器进程都已退出；
3. `sc.exe query clash_verge_service` 返回 1060，或当前版本卸载器无法继续；
4. 已经保存了第 1 节的诊断输出。

即使满足这些条件，也只备份和处理明确的锁/运行时状态文件，绝不删除整个 `C:\ProgramData\clash-verge-service` 或用户应用数据目录。大多数“服务 RUNNING 但内核不能启动”的实例不是旧锁，而是属主、token、协议或运行时问题。

## 5. 给其他 AI 的完成标准

若让 GPT-5.6-Sol 或其他工具依据本文件执行修复，其最终报告必须包含以下证据：

- 实际应用数据目录，以及是否为便携版；
- 当前应用目录和实际使用的服务安装器路径；
- 服务查询结果；
- 修复前后根目录与 token 的属主；
- 最后一条 Service/Core 错误，或同一次启动中的两条成功日志；
- TUN 是否真正启用。

缺少 `Starting core in service mode` 和 `服务成功启动核心` 时，报告必须标记为“尚未修复”，并附上日志，而不是以 `RUNNING` 结案。
